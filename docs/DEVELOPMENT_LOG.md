# Development Log

2026-10-09 — 0.6.0 released: a sale ticker under the board, and the row that was never there

- `plugin.yaml` goes 0.5.1 → 0.6.0, tagging three changes that had accumulated since the last release: OpenRouter becomes a visible provider row (2026-10-04), the settings page says in one line what each provider's credential needs (2026-10-03), and the panel gains a third layer below the balance zone.
- **The sale ticker.** A strip under the board that scrolls left through the models the portal is currently discounting or giving away: `provider/model` in full, a `NEW` capsule for `featured_models`, a `REASONING` capsule from `capabilities.reasoning`, the discount capsule, and the current `$in / $out` price with the original struck through as one group. Data comes from the gateway's `model.options` — the same read-path call the model picker makes, cache-only and non-blocking, so the plugin's Python half is untouched — polled every 5 minutes, and every 30 seconds while a row is still `pricing_pending` / `free_tier_pending` so a cold cache warms quickly.
- **What counts as a sale, and what does not.** A discounted entry needs `discount_percent >= 1` *and* an original price: a bare `-100%` with nothing to cross out is not drawn, because it would claim a saving the row cannot show. A free model shows its name and a `FREE` capsule and no prices at all. A row that is pending, or whose `pricing` is empty, produces nothing rather than a guess.
- **Reading it by hand.** Hovering pauses the scroll; while paused the wheel scrubs the strip horizontally and a left-drag scrubs it by hand, both sharing the offset with the automatic scroll, so letting go resumes from where it stopped instead of jumping back. The wrap-around point is measured from the real cycle (the second copy's first item minus the first copy's first item), not `scrollWidth / 2` — the two differ by `(n−1)·gap/2`, which reads as a jump on every loop.
- **Per-platform switches.** A provider whose row carries a pricing signal gets a third switch in its settings card, stored per platform under one `localStorage` key (an older single boolean migrates to `{nous: …}` and is not lost). Turning a platform off drops only that platform's entries. Switching profiles clears the rows first, so the previous profile's sale never backs the next frame.
- **Upstream limit, stated rather than hidden:** the gateway attaches `discount_percent` / `was_*` to Nous Portal rows only ("Sale chrome is Nous Portal-only"). Measured on a live payload, `nous` yields 46 entries (39 discounted with an original price, 7 free) while every other configured provider carried no pricing at all, so no other switch rendered. Nothing in the panel needs to change when the gateway opens this up.
- Tests: frontend **209/209** (new `tests/sale-ticker.test.mjs`, 14 cases — including a frame-by-frame replay of the marquee loop against a fake DOM, proving the cycle measured is the real one and that pausing and resuming neither drift nor jump); backend **165 passed** with `hermes_cli` importable. Deployed through `tools/deploy.mjs`: runtime sha `fabbeac042e0`, previous kept as `.last-good`, no error-boundary in the following watch window.

2026-10-04 — OpenRouter: the row itself was missing, not just its balance

- Started from "why does the meter not show my OpenRouter balance?". Two layers, and the first one mattered more: OpenRouter is *not* in Hermes' `PROVIDER_REGISTRY` env-slot table (it is a routing provider named in `config.yaml`, not a registered auth entry carrying `api_key_env_vars`), so the discovery layer never produced a candidate for `OPENROUTER_API_KEY` — the provider never appeared on the board or the settings page at all, not even as a `no_fetcher` placeholder. Fixed the way `xai` already handles a credential the registry does not know: declare it under `ledger_env` (env name is the identity). The candidate now arrives via the ledger path.
- The fetcher: `_fetch_openrouter` reads two endpoints with the same plain `sk-or-` key — `/credits` for the balance (`total_credits − total_usage`, USD) and `/key` for the spend columns (`usage_daily` / `usage_weekly` / `usage_monthly`). The docs call `/credits` "management key required", but the plain inference key returned 200 (checked 2026-10-04), so no second credential is asked for. The spend figures are **calendar windows** (UTC day / Mon–Sun week / month), not the rolling 7d/30d the other providers use — OpenRouter gives a plain key no rolling windows (`/activity` → 403 "Only management keys can fetch activity"), so this is the zero-config ceiling. Spend is optional: if it fails the row keeps the balance and goes `partial`.
- Wiring: one `FETCH_BY_ID` binding; `_ACTION_HINTS["openrouter"]` stopped saying "no fetcher adapter yet" and now names the env var; the settings page's `Needs:` line derives from `ledger_env`, so no `meta.credentials` block was needed.
- Neal's rule from the same thread (2026-10-04), to be generalised later: **if the numbers need no extra setup, show them by default; if they need extra configuration, hide them by default and say on the settings page how to turn them on; a provider that cannot show them at all says so instead of pretending.** OpenRouter is the first case (zero-config → shown). The general switch is not built yet.
- Tests: `tests/test_openrouter_balance.py` — 11 cases (discovery through the ledger slot, balance + spend happy path, spend 403 → `partial`, zero usage kept as real zeros, bad spend shape → `partial`, three bad balance shapes → error, missing credential, 401 and 403 both → `auth_error`, and the `build_payload` binding proving it is a real fetch and not a placeholder). - Three colour requests and one honesty request, all built in one pass. (1) Balance rows carry colour again, on the two things you actually read: the dot before the account name and the balance amount itself — `TODAY` / `7D` / `30D` stay neutral, the request named the balance only. (2) A row you cannot call right now goes grey, plan and balance alike: balance 0, balance at its cap, 5-hour window spent, weekly window spent. - **Two accents per provider, one per theme.** A single value cannot be legible on both a white card and a dark one: clearing 3:1 on both leaves only L* 47–62, a fifteen-wide band, and the values that survived it were dark enough that the balance amount vanished in the dark theme — which is what sent Neal back to the keyboard. `identity.yaml` now carries `meta.accent` (light) and `meta.accentDark` (dark); the row picks by the theme the host is rendering (`readColorScheme()` reads the host's inline `color-scheme`, falls back to `prefers-color-scheme`, then to light, and never throws), and a row without a dark value keeps using `accent` so old payloads still paint.
- **What the accent threshold is, and what it deliberately is not.** Supplier accents are decoration — they say which company a row belongs to, and nothing depends on telling two of them apart. So the only rule is legibility on the theme in question, and it is **4.5:1**, not the 3:1 that a chart mark needs: the provider name and the amount are 10px text. The pairwise ΔE ≥ 15 floor and the Machado colour-vision simulation were applied to this palette earlier the same day and produced a fake impossibility — under those constraints plus the three state colours, Command Code had a ceiling of ΔE 12.6 in the light theme, because the constraints had pushed every accent into a single hue axis. Both constraints belong to the **matrix** palette, where colour carries the functional meaning (available / surplus / over-consumed), and they are unchanged there. Each brand keeps its own hue: only lightness moves, and only on the theme where the brand colour would not read (`tools/fit-brand-accent.py`).
- **Grey is a row state, not a new quota tier.** One `UNAVAILABLE_GRAY` (`#404040`) joins both palettes under the `gray` key — `paletteFor(mode)` stays the only entry point — and the legend gained a swatch and a sentence for it, because a legend that does not mention grey is worse than no legend. Balance rows get their own arm in `availabilityOf` (balance 0, or `accent === 'cap'`), so ranking and colouring read the same verdict instead of inventing a second one. The matrix cells are untouched: being out of quota greys the row, it does not recolour the grid.
- **Balance rows sort among themselves.** They already sat below every plan row (2026-09-26); now the group is ordered by balance, largest first, and a row with nothing left — 0, missing, unparsable — sinks below the ones that still have something. Plain numeric comparison: balances are in each provider's own unit (¥, $) and are not converted. Ties and "both empty" keep the backend's order, so a poll that changes nothing does not reshuffle the board.
- **A recognised credential without an adapter keeps its row.** `XIAOMI_API_KEY` (MiMo, balance only) resolved to a provider with no fetcher and simply was not drawn — indistinguishable from a broken plugin. `build_payload` now emits a placeholder row: the name, no numbers, `gap="no_fetcher"`, and "No fetcher adapter yet" in the value slot with the reason in the tooltip. `usedPercent` became nullable in the same pass, because "no data" and "used 0%" were the same value in the payload and the front end was entitled to draw a full bar for the first. The placeholder takes its `kind` from `identity.yaml`, so a balance-only provider lands in the balance zone rather than the plan zone.

2026-09-26 — colour-vision mode: a second palette, an outline, and copy that follows both

- The five cell colours were picked on 2026-09-12 without a colour-vision check. Under a full-strength Machado simulation the worst pair in the default palette is `#14AE68` (available) against `#28A7E0` (surplus): CIELAB ΔE 12.3 for a tritanope — the same colour — and their WCAG relative-luminance contrast is 1.06:1, far under the 3:1 that §1.4.1 accepts as a distinction other than colour. Protanopia and deuteranopia stay at ΔE ≥ 24; this is a blue-blind failure, not a red-green one, which is why it had gone unnoticed.
- The fix follows what three shipped systems do, all the same shape. WCAG 2.x §1.4.1 forbids colour as the only carrier and names the lightness escape hatch; Apple's "Differentiate Without Colour" replaces colour-only cues with shapes; Discord's Colorblind Mode arrived as icons on statuses, not as a recolour. So the mode does both: `HIGH_CONTRAST_COLORS` swaps the three semantic hues (green `#228833` available, yellow `#F0E442` surplus, `#EE6677` over-consumed — Okabe & Ito's colour-universal set) and every cell gains a 1px outline. The outline is not decoration: the bright yellow's contrast on a white card is 1.32:1, so the cell needs a boundary that colour cannot give it.
- Rejected the obvious vermillion `#D55E00` for the over-consumed hue: under deuteranopia it lands at ΔE 5.4 from the darkened yellow of the locked surplus segment, and the lightness fallback reaches only 2.92:1 — still short of 3:1. `#EE6677` separates from that dark yellow by 33, so it needs no lightness crutch.
- The legend now follows the palette: `Sky blue` / `Dark blue` / `Orange` become `Yellow` / `Dark yellow` / `Red` while the mode is on, and the swatches wear the same outline — a legend naming colours that are not on screen is worse than no legend.
- The switch sits in a new `Display` block and is stored per machine (`localStorage`), not per profile: it describes the eyes in front of this screen, which is also how Apple's toggle behaves. Storage that throws (private mode, sandboxed host) reads as default rather than failing, and the change reaches the board through the existing `subscription-meter:settings-changed` event, now sent by `notifySettingsChanged()` so a host without a global `Event` cannot break the panel.
- `tests/color-modes.test.mjs` pins the reasoning, not just the hexes: the default palette must stay under 15 ΔE (12.3 — the reason the mode exists), the new one must clear 15 (18.9) and pass 3:1 on the available/surplus pair (3.42:1), the tritanopia gap is asserted on its own, both palettes are byte-locked, storage round-trips and degrades to default, and source assertions cover the switch, its copy and both outlines. Written RED first: the file fails whole against the previous build.
- Frontend suite: 163/163. Deployed through `tools/deploy.mjs`: runtime sha `61ee5d33`, no error-boundary afterwards.

2026-09-26 — availability gate: a window you cannot use never leads the board

- Sorting had exactly one dimension (the main window's surplus pace, 2026-09-09) and deliberately kept the 5h burst window out of it (2026-09-10). That is still the right call, but it left the board blind to a different fact: an exhausted burst window means the account cannot be called at all. Live case: Codex sat at 100% of its 5h window and 97% of its weekly window (server reported `allowed: false`) yet its weekly row ranked first — with 2.8% of the window left, the `÷ (1 − elapsed)` denominator had turned a 0.2% surplus into P = 0.074, ahead of GLM with 98% remaining.
- `orderRowsForDisplay` now tiers rows: callable first (unchanged priority formula), then not-callable rows (main window or burst window exhausted) ordered by unlock time, then rows with no usable reset moment, then balance rows. `availabilityOf(row, sibling)` is the single predicate; `burstShare` deliberately takes no part — it decides how long the locked segment is drawn, not whether the row can be spent. A row blocked by its burst window unlocks at the burst reset; one that burned its main window unlocks at its own.
- Live before/after on one payload: `codex(3% left) → kimi → glm → grok` becomes `kimi → glm → grok → codex`. `tests/availability-gate.test.mjs` pins the live case, "large locked segment but still callable", both unlock times, rows without a share, and the automatic return to priority order once the window resets. Frontend suite: 156/156.

2026-09-26 — deploy guard: atomic replace, previous-build slot, log sentinel

- Deploying the panel used to be a plain copy into the directory the app watches. That makes every intermediate state of a multi-step edit live code — a temporarily duplicated declaration or a missing const is executed on save — and it left no way back when a build turned out to be broken at runtime. `tools/deploy.mjs` now runs the frontend suite, keeps the previous build as `plugin.js.last-good`, writes the new build to a temp file and `rename`s it over the live path (one atomic action, no half-written file ever visible), records a `deploy-receipt.json` (both hashes, timestamp), and then watches the app log for a few seconds.
- The sentinel only reacts to lines that name this plugin and are newer than the deploy, so an unrelated plugin's crash does not roll this one back: on a fresh `error-boundary` / `React error #310` entry it restores `.last-good` atomically, marks the receipt, prints the offending lines and exits non-zero. `tools/rollback.mjs` does the same restore by hand.
- `tests/deploy-guard.test.mjs` exercises both scripts against a temporary runtime directory and log file: atomic replace plus `.last-good` plus receipt, first deploy with no previous build, automatic rollback on a fresh failure, ignoring other plugins and stale log lines, and manual rollback refusing to touch the runtime when there is nothing to restore.
